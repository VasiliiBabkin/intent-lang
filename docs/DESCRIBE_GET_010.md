# Sedrava 0.10 — Describe → Get contract (proposal)

Status: **records/task-manager integration is experimental on the development branch**; see [measured report](COLLECTIONS_010_REPORT.md). Named screens and the two-screen task manager are implemented on the navigation branch; see [navigation coverage](NAVIGATION_010_REPORT.md). Remaining product gates include package identity and broader accessibility/device acceptance. The [first-class text increment](LANGUAGE_0_10_TEXT.md) is implemented on its development branch; the illustrative natural-language sketch below is not the adopted grammar. Executable records/navigation syntax is specified in their language contracts. Sedrava 0.9.0a1 is the published compatibility baseline.

## Non-negotiable product promise

**Describe the application; get the application. / Опиши приложение — получи приложение.**

An author declares *what* data exists, *what* the user can do, *which* constraints must hold, and *what* outcome should be presented. The compiler/runtime supplies the rendering, persistence adapter, validation, state transitions, accessibility defaults and platform plumbing. A source file must not require user-authored Kotlin, JavaScript, HTML, SQL, navigation controllers, callbacks, lifecycle code or database migrations for the reference use case.

A native Android experience and a Web experience may look different, but the accepted/rejected state transitions and visible meaning must agree. This is **deterministic generation**, not a promise of AI-generated code or natural-language understanding.

## Reference outcome: personal task list

A single declarative source describes a small offline task manager: add a named task, mark it complete, view active/completed tasks, remove an entry, and reopen the application with accepted data intact. It has a list and a task detail view; on a narrow phone and in a browser it remains usable. Android and Web must both be generated by the standard CLI.

A reader should be able to reproduce it from a clean checkout without editing generated files. Generated artifacts are replaceable and rebuildable.

## Language evolution — semantic dependencies first

1. **Text values:** bounded UTF-8 string state, deterministic equality, length/empty checks, validated text input, explicit limits, escaping and persistence. Specify Unicode normalization and limits before implementing.
2. **Records and collections:** typed task record and bounded ordered collection, stable record identity, atomic add/update/remove, validation of every element and restoration. Specify collection equality, capacity, index/identity semantics, schema version and migration/fallback policy.
3. **Declarative UI:** list from a collection, cards, text field, toggle, detail view and navigation based on declared state; keyboard and screen-reader semantics; platform-appropriate layout and light/dark theme defaults.
4. **Minimal orchestration:** high-level operations such as add/complete/remove should compile to the same atomic state transitions as 0.9 actions. Do not expose mutable framework event handlers.

No arbitrary expressions, host-language snippets, hidden network dependency, implicit data exfiltration or background services. Avoid feature names or syntax that imply functionality before conformance tests exist.

## Proposed author experience (illustrative pseudocode; NOT VALID SEDRAVA)

```text
app "My Tasks"
data tasks: list of Task
  Task: { id: stable-id, title: text(max=120), done: bool }
  persist
operations:
  add task with title (require title not empty)
  complete task by id
  remove task by id
views:
  tasks: list tasks showing title and done; allow add, complete, open
  detail: selected task; allow complete, remove, back
```

This is a *behavioral target*, not an adopted grammar. The actual grammar must be specified with parser examples, failure diagnostics and backend conformance before use. Aim for a concise source; reject a design that forces authors to manually wire every widget and callback.

## Required deliverables and acceptance

- Versioned syntax and normative semantics with backward compatibility tests for every 0.9 example and CLI command.
- Same source yields a working Android APK and standalone Web application, with no post-generation edits.
- New state and actions tested against the interpreter and both generators; browser integration and Android JVM/UI tests where an emulator or physical device is available.
- Invalid input and invalid persistence cannot mutate accepted state. Collection mutations are atomic; capacity, string limits, duplicate IDs and invalid selection are deterministic.
- Navigation survives rotation/recreation as specified; saved tasks survive restart; no cross-app Android package collision for newly generated apps.
- Keyboard navigation, semantic labels, scalable typography and contrast checks; explicit limitations where verification is unavailable.
- Fresh-user Quick Start: clone, check, test, build Web, build Android and run the reference app.
- CI reports measured evidence, not implied platform coverage. Do not publish 0.10 or create a tag without release gates and explicit approval.

## Anti-goals / Не делаем

- A verbose wrapper around Kotlin Compose or React.
- A form-builder that only paints screens without real application behavior.
- Unspecified magic inference or mandatory AI/cloud services.
- Arbitrary plugins or permissions as a shortcut for missing language semantics.
- A feature-complete Sedrava IDE in 0.10; this release should make a future Sedrava-authored editor more feasible.

## Implementation sequence

First lock down strings and collections in the core, with executable conformance tests. Next add high-level operations and their atomic semantics. Then generate the list/detail UI on Web and Android. Finally test the real task app end to end and document the supported subset. If the whole target cannot be verified, label the result an intermediate development milestone rather than claiming a completed 0.10.
